# Pipeline documentation

Every pipeline built, changed or evaluated gets a Documentation doc with the pipeline's name, written with
`write_documentation` in Markdown. The same content is returned in the chat. On an update, revise the sections
that changed; the tool keeps the change log and adds a line to it.

## Sections

| Section | Events pipeline | Indexing pipeline |
| --- | --- | --- |
| Purpose and data | Feeds, source system, record format, volumes, the sample files used | Source feed, destination index, Elastic Cluster |
| Processing | Element chain, inherited template, reference data and dictionaries, decoration | Element chain, inherited template, enrichments |
| Field mapping | Generated by the tool (below) | Generated by the tool (below) |
| Output | Anything beyond the Field mapping's counts: volumes, Events streams produced | Index template name and version; verification searches and results |
| Conformance | Schema validation and quality pass rates; recent error groups | Error stream triage summary |
| Open items | Suggestions and known limitations; input fields not mapped | Suggestions and known limitations |

## Field mapping: generated, never typed

`write_documentation` writes this section itself. It reads the mapping (or index plan) kept with the pipeline's
XSLT, which `build_translation_xslt` stores when it saves (`build=`, `name=`), or `save_xslt` when given
`index_plan=`, steps it over the
`stream_ids` you pass (the sample raw streams for an events pipeline, the Events streams for an indexing
pipeline), and puts the result in place of whatever the markdown has under `## Field mapping`. So:

- Save every generated XSLT with its mapping (`build_translation_xslt build=... name=...`, or `save_xslt
  index_plan=...` for an indexing XSLT). Without it, an events pipeline's doc
  must bring its own `## Field mapping` section, and the tool refuses one that does not.
- Pass `stream_ids` to `write_documentation`. `build_translation_xslt` with `pipeline_uuid` and `stream_ids`
  returns the same section as `field_mapping`, to read before writing the rest of the document.
- Change the mapping and regenerate rather than editing the XSLT: `build_status` reports an XSLT that is no
  longer what its mapping generates, and a documentation whose Field mapping predates the current mapping or
  XSLT (a digest marks the section).

### What the section holds (events pipelines)

How records are read, when it applies: `for_each` (one record, several events), the kinds left untranslated
(`drop_when`, with the reasons), and the fields `extract` parses out of text.

**EventSource** (and `EventTime`): one row per element, with columns XPath, Description (the event-logging
schema's own), From (the mapping: `` `badge_user` (lower)``, `` lookup `USER_DIRECTORY` by `user` -> `name` ``,
`` first of `time`, `timestamp` ``, `` `roles`, one per value ``, a constant in quotes, a value map as
`ok -> true, fail -> false`), and Sample values: the values the sample's events got, up to three, then how many
more; "(logon events only)" when only some kinds of event have the element; "(several per event)" for repeats;
"(not in the sample)" when no sampled event got it. An element the sample's events have that the mapping does not
write (a hand edit, a later step) gets a row saying so.

**Event types**: one row per rule, with columns Rule (name and conditions), TypeId and Description (From, then the
values seen), Events (how many of the sample's events the rule wrote, exactly: the documentation run marks each
Event with its rule), and EventDetail: every other element below `EventDetail` as `` `path` <- from = "sample
value" ``. Drop rules show as left untranslated. Events no rule of the mapping wrote are counted at the end.

### What the section holds (indexing pipelines)

The index name, backend and time field; events left out (`drop_when`); and one row per index field: name, type,
the event-logging path it comes from, and how often that path is populated in the sampled Events.
